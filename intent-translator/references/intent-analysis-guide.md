# 意图分析与需求判断指南

本文件为意图转译师提供分析参考。它不是要求每次输出的固定表单；仅在有助于理解和转译时使用。

## 1. 从原话到意图

建议按以下顺序理解：

1. **原话**：用户明确说了什么？
2. **上下文**：这句话回应了什么、补充了什么、否定了什么？
3. **问题**：用户目前遇到的障碍是什么？
4. **目标**：用户希望事情最终变成什么样？
5. **行动**：接收方需要做什么？
6. **验收**：怎样判断结果符合用户期望？

不要跳过上下文，直接根据单句生成任务。

## 2. 需求信息分类

### 用户明确表达
用户直接说出、明确确认或明确选择的内容。可以作为确定要求。

### 合理推断
根据上下文推导出的可能意图。应标记为推断；如果推断会改变方案，需要确认。

### 专业建议
转译过程中发现的可选改进。应独立标记为建议，不得混入用户的强制要求。

### 待确认事项
有多种合理解释，且不同解释会改变范围、方案或交付结果的信息。

## 3. 要求强度识别

| 表达 | 默认理解 | 注意事项 |
|---|---|---|
| 必须、一定、不能、只允许 | 强要求 | 仍需检查上下文是否有后续修正 |
| 需要、要、请完成 | 明确要求 | 通常作为任务要求 |
| 希望、最好、尽量 | 倾向或期望 | 不自动升级为硬性约束 |
| 可以考虑、不妨、例如 | 建议或示例 | 不等于必须实现 |
| 不要、避免、保留、不改变 | 负面约束或保留项 | 需要明确作用范围 |
| 我觉得、可能、是不是 | 观点或假设 | 不应写成已证实事实 |
| 比如、例如 | 示例 | 除非用户说明，否则不要视为完整清单 |

## 4. 多轮对话更新规则

将当前需求视为一个持续更新的版本，而不是消息列表。

- 用户补充新要求：增加到对应位置。
- 用户明确纠正：替换旧内容。
- 用户撤回要求：删除该要求。
- 用户改变目标：重新评估整个需求结构。
- 用户只表达疑问：不要误判为已决定修改。
- 用户提出反例：判断是新增边界、修正规则还是单个案例。
- 用户表示“其他保持不变”：只修改指定部分，保留其他已确认内容。

更新后检查依赖关系。例如，用户删除某项功能后，相关测试、交付要求或验收标准也可能需要同步调整。

## 5. 冲突判断

冲突不一定意味着两条要求互斥。先判断：
- 是否属于不同用户角色；
- 是否适用于不同场景；
- 是否处于不同阶段；
- 是否一条是目标、一条是实现偏好；
- 是否后续要求明确覆盖前面的要求。

只有无法兼容且影响结果时才追问。

## 6. 何时应该追问

适合追问：
- 目标对象不明，导致内容结构会明显不同；
- “优化”没有明确对象，且无法从上下文判断；
- 用户要求自动执行，但权限或确认边界不清；
- 用户要求修改项目，但没有说明是只分析还是允许改动；
- 多个互斥方案都会影响最终结果；
- 时间、地区、版本等条件对事实准确性至关重要。

通常不必追问：
- 可由接收方先检查环境后确定的实现细节；
- 不影响核心结果的格式偏好；
- 用户已授权执行者自行选择的事项；
- 能明确标注为假设且风险较低的信息。

追问一次只聚焦一个关键点。用户回答后继续整理，不要重复提问。

## 7. 避免“过度完整”

以下情况不应自动加入需求：
- 没有场景依据的极端边界；
- 与核心目标无关的额外功能；
- 用户没有要求的复杂审批流程；
- 不必要的技术选型；
- 无法验证的绝对化承诺；
- 只是为了让文档看起来专业而增加的章节。

是否增加一项内容，判断它是否会实质改善用户目标、执行正确性或风险控制。
