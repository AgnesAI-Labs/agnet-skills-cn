# 用户反馈分析 | User Feedback Analysis

将零散的意见、评价、建议和投诉，转化为**有出处、能区分事实与推断、可用于下一步行动**的洞察。面向个人、商家、创作者、教育机构、服务团队、产品和运营人员等通用场景；不预设行业或固定分类体系。

## 何时使用

- 用户要求整理、总结、归类或深入分析评论、评价、投诉、问卷、访谈、客服记录、社群讨论等反馈。
- 用户关心用户/客户/参与者“主要在说什么”“满意/不满什么”“有哪些潜在需求”“哪些问题先改”。
- 用户要求分析反馈的正负面主题、共性、分歧、频次、群体差异或时间变化。
- 用户希望将已有反馈转为可追溯的分析报告、反馈明细、需求机会清单或行动建议。
- 允许用户直接提到“反馈分析”“评论分析”“用户声音”“VoC”“reviews analysis”“survey comments”“interview synthesis”等自然表达；无需指定 Skill 名。

## 不应使用 / 与其他任务分工

- 没有任何反馈材料、只要求原创市场调研或猜测用户偏好：说明所需材料并协助设计收集方案，**不伪造反馈**。
- 用户主要要求自动抓取、访问私密系统、发送客户回复、操作产品、执行 A/B 测试或发布内容：这些不是本 Skill 的直接职责；若其他可用工具可合法执行，由用户授权并明确区分。
- 不把本 Skill 当作临床心理诊断、法律裁决、审计鉴证、严格代表性民意调查或因果推断工具。

## 总原则（始终遵守）

1. **先回应实际任务。** 简单问题先直接给出结论，不机械地输出六步分析或多份文件。任务复杂、用户要求可交付文件时再使用完整流程。给用户的最终回复必须本身包含分析正文：材料范围、编号、原话、结论，以及明确诉求和推断的区分。待办清单、草稿或内部记录不能代替回复。禁止只写「上面的分析就是完整回复」「已经分析过」而不把分析写在这条可见回复里。
2. **不编造。** 禁止捏造来源、原话、样本、数字、统计结果、群体身份、日期、引用链接或已完成的外部操作。
3. **证据与推断分离。** 明示“原始反馈/可观察事实”“分析归纳”“待验证假设”“建议行动”。用户没有明确提出的功能方案不能写成“用户要求”。
4. **保留追溯。** 有条件时为每条原始反馈生成稳定 `反馈编号`，记录来源/时间/原始位置，并为重点结论提供至少一条可核验原话及编号。无法追溯时标明限制。
5. **统计口径清晰。** 严格区分“原始记录数”“去重后记录数”“独立反馈者数（仅可识别时）”“主题提及次数”；一条反馈可以命中多个主题，主题次数之和可大于记录数。所有比例说明分母。写出分项次数时，声明的合计必须等于各分项相加；对不上就改合计，不保留错误总和。
6. **不以频次取代重要性。** 严重的低频问题仍可能优先处理；不把“高频”直接等同“影响人群广”。样本限制写明之后，影响范围就停在这些记录上，不写「影响面可能更大」「往往还有更多人遇到」或同类扩样句。
7. **保护隐私。** 默认只处理用户提供或经授权可访问的数据；对外分享报告时按需删除或掩盖个人身份、联系方式及其他敏感字段。不得通过工具绕过权限。
8. **尊重用户指定输出。** 用户只要总结就不要硬生成 Excel；指定 CSV、XLSX、Markdown、JSON 时尽量按可用能力生成。没有文件能力时给出可复制内容，不伪称已生成文件。

## 工作流程：根据任务深度自适应

### 1. 识别任务与资料

- 确定分析目的（解释现状、找问题、发现机会、比较群体、比较时间或制定改进计划）、评价对象、已有数据、分析范围、输出形式。
- 输入可为聊天文本、CSV/Excel、访谈笔记、问卷结果、客服导出、PDF/文档、公开评价等**用户提供或已授权访问**的数据。读取能力取决于宿主环境；无法解析的附件应说明并请求可处理格式。
- 没有提供分析目标时，从用户问题中合理推断“总结主要反馈并给出依据”；不要因此阻塞处理。
- 缺失的时间、受访人身份、地区、产品版本、评分尺度等字段标“未知/未提供”，不得补造。
- 文件很多或输入很大时先核对可读取范围；必要时分批处理，并在报告中披露已分析/未分析的记录及筛选口径。

### 2. 清洗与建立反馈记录

- 尽量一条独立消息/一次回答/一条工单作为一条`原始记录`；保留原始文字，不把不同人的反馈拼成一句“原话”。
- 给每条记录一个稳定 ID（例如 `F001`）；拆出多个主题时用 `F001#1`、`F001#2` 作为`提及ID`，保留同一原始 ID。
- 识别明显重复和转发，分别记录原始数与去重数；无法确认同一反馈者时，**不要按文字相似推断为同一个人**。同一问题由不同人多次反馈仍可计入不同记录。
- 标明空文本、乱码、无关记录、无法判断意图等情况；不要在不告知的情况下丢弃会改变结论的数据。

### 3. 根据材料建立可解释的分类

- 允许一条记录同时包含多个主题、不同态度或互相矛盾的诉求。记录级情绪与“主题提及”级情绪可不同。
- 提取：反馈主题、评价对象/环节、情绪（正面/负面/中性/混合/无法判断）、明确诉求、问题或亮点、可能的根因**假设**、原始证据、判断信心。
- 优先用数据中出现的主题命名；避免套用仅适用于互联网产品的固定分类。参阅 [反馈分类规则](references/feedback-taxonomy.md)。
- 对含有讽刺、模糊表达、转述他人意见或中英混杂的反馈，保留不确定性，不把情绪判断当作心理诊断。

### 4. 归纳洞察，并仅在条件具备时做对比统计

- 提炼：主要正向亮点、主要痛点、具体建议、少数但严重的问题、互相矛盾的诉求、潜在需求与待验证问题。
- 有可计数记录时按`反馈记录数`或`主题提及次数`输出频次，并写明分母、是否去重、是否多标签和样本时间窗；不能计算时只做定性分析。
- **群体比较**要求有真实的群体标签；**时间趋势**要求有可靠日期与可比口径。分组数据不足、来源偏差太大时改为“观察”，不武断判断趋势。
- 不从满意度分数推断用户动机，不以相关性写因果。参阅 [分析方法](references/analysis-methods.md)。

### 5. 将反馈转为建议，但保持可验证

- 每条改进机会应包含：观察到的问题/价值 → 证据（反馈 ID、原话或数据）→ 推定的需求 → 可选改进方向 → 影响与不确定性 → 建议验证方式。
- 优先级可分 P0/P1/P2/P3 或高/中/低，但要解释所依据的严重度、影响范围（有证据才写）、发生频次、紧迫程度和可执行性；禁止伪造精确权重、ROI 或成本。
- 若数据只足以证明“有人提到”，就提出验证问题而不是硬给确定性产品结论。
- 在回答中优先呈现 3–7 个最有行动意义的发现；其余放到附录/表格。参阅 [证据与隐私规范](references/evidence-quality.md)。

### 6. 选择合适的交付深度

| 任务层级 | 默认行为 | 可选交付 |
| --- | --- | --- |
| 快速分析：少量文字/单一问题 | 直接给观点、代表性原话、下一步建议 | 对话内总结 |
| 标准分析：批量评论/问卷/客服记录 | 分类、计数、主要问题、需求机会、样本边界 | 反馈主题归类.xlsx、需求与改进机会.xlsx，或 CSV |
| 深度分析：多个来源/群体/时间 | 标明数据口径、对比、分歧、优先级、证据链、限制 | 反馈分析报告.md + 明细/需求清单 |
| 专项输出：指定表格/报告/主题 | 严格遵从用户要求，不强加别的内容 | 选定格式 |

- 需要文件时优先使用宿主已提供的文档/表格创建能力；如果环境无法导出 XLSX，则交付 UTF-8 with BOM 的 CSV，明确说明格式差异。**不声称无能力时也能生成可下载文件。**
- 文件字段可采用 [反馈记录模板](templates/feedback-records.csv)、[机会清单模板](templates/opportunities.csv)、[报告模板](templates/report-template.md)；按任务删减字段，不强制填写无依据的信息。
- 若引用的公开第三方来源需要核对，按可用检索能力核查并标记来源；无工具时不得宣称“已经核验”。

## 最小输出质量标准

1. 用户可见的最终回复本身包含分析正文。不得用待办、草稿或「上面已经分析过」代替编号、原话和结论。
2. 开头清楚交代分析了哪些材料、样本/时间范围及当前结论的适用边界。
3. 重要观点有对应的反馈 ID、原话或原始出处；引用保留上下文，不断章取义。
4. 数字可复算；无法确认的去重、身份、时间、母体和样本代表性已标明。
5. 至少区分“观察到的事实”和“建议/假设”；重要分歧或反例不得隐藏。
6. 对用户提出的问题有直接结论及可执行下一步，不堆叠空泛的研究术语。
7. 未读取、无法解析、处理失败的文件或条目明确披露。

## 示例

**输入**：“这是 20 条客户留言，帮我看看主要不满意什么，哪些要先改。”  
**行为**：列出不满主题及其反馈记录数/20，附代表性原话与 ID；单独标记低频高严重度问题；用证据和待验证项说明优先级。若未要求文件，直接在对话中输出。

**输入**：“给你三个月的课程反馈，比较新学员和老学员的意见，并生成 Excel。”  
**行为**：仅使用有可靠日期/学员标签的记录分组，对缺失项单列“未知”；采用一致口径计算主题差异，生成表格，明确不可比之处；不自行推测谁是新学员。

**输入**：“我只有两条差评，你告诉我是否代表大多数人都不满意。”  
**行为**：分析两条反馈的具体问题，但明确无法代表整体满意度，建议补充样本和用户行为/量化数据。

**输入**：“根据这些访谈，帮我列出用户明确提出的需求以及你推断出的机会。”  
**行为**：将`明确提出`和`分析推断`分栏，原话对齐每一条需求，给推断标注待验证证据。
