# 反馈分类、情绪识别与需求提炼规则

本文用于指导 Agent 在不同业务中使用**可解释、可调整**的主题分类，不是行业固定标签库。先观察数据，再命名类别。

## 1. 三个互不替代的分析维度

| 维度 | 问题 | 示例 |
| --- | --- | --- |
| 主题 / 对象 | 反馈涉及什么？ | 服务速度、内容清晰度、商品质量、课程进度、网页加载 |
| 评价 / 情绪 | 反馈对该主题持什么态度？ | 正面、负面、中性、混合、无法判断 |
| 诉求 / 行动 | 用户希望改变什么？ | 提供字幕、减少等待、保留进度、保留优点 |

不要用“负面”当作主题，也不要把“要求退款”直接等同于对每个方面都不满。优先通过原话判断。

## 2. 如何创建主题体系

1. 先审阅资料中的实际高频词和场景，形成 5–12 个可解释的初始主题；如果数据很少，主题可以更少。
2. 主题名称尽量使用普通用户能理解的语言，比如“配送速度”“课程内容”“售后沟通”，避免空洞标签如“其他体验问题”。
3. 一条原始记录可有多个主题。编码时同时保留原始记录 ID 和每条主题提及 ID。
4. 同义表达合并，例如“卡住”“加载慢”“一直转圈”可合为“加载/性能”，但具体含义不同的不能强行归一。
5. 当“其他”占比过高时检查是否漏了类别；当类别过细而每类只有一条时可合并上位主题，但保留原话细节。
6. 保留一个可选“无法分类/信息不足”类别，不要为了得到漂亮的统计强行分组。

**通用一级主题候选（只做起点）：** 质量/可靠性、速度/效率、价格/价值、可用性/操作流程、内容/功能、服务/沟通、售后/保障、信任/安全、正向体验、意见/建议。教育、公共服务、线下活动等场景应按真实情境调整。

## 3. 情绪判定

| 分类 | 判定线索 | 误判注意点 |
| --- | --- | --- |
| 正面 | 明确肯定、满意、感谢、推荐或赞扬 | 不能因为提到“好”就忽略反讽 |
| 负面 | 明确不满、障碍、抱怨、失望、投诉 | 描述故障可标负面，但也可能是中性报障 |
| 中性 | 客观提问、陈述情况，未表达喜恶 | 不把“如何使用”直接判成差评 |
| 混合 | 同时认可某些方面并批评另一些方面 | 应按主题分别标注情绪，不抹平差异 |
| 无法判断 | 信息过短、反讽不明、文本缺失 | 不强制赋予情绪 |

不做没有依据的“愤怒指数”“真实心理状态”等心理推断。可结合星级/评分但注明评分维度和来源，冲突时保留冲突。

## 4. 四层提炼：从原话到行动

| 层级 | 示例 | 证据性质 |
| --- | --- | --- |
| 原话 | “每次进来还要重新找上次看到哪里。” | 用户确实表达的内容 |
| 观察到的问题 | 用户需要重复寻找学习位置 | 贴近原话的归纳 |
| 推测的需求 | 希望降低继续学习的操作成本 | 待验证的解释 |
| 可选方案 | 自动保存进度/提供最近学习入口 | 方案建议，不是用户原话 |

用户**明确说过**某个方案时可标“明确需求”；否则应写“推断需求”或“改进方向”。一个问题可能存在多种合理解法，应避免在没有验证的情况下单一化。

## 5. 常见特殊文本

- “挺好，但是手机端老闪退”：记录正面和负面两个主题/提及，整体情绪可为“混合”。
- “别人说你们的客服很差”：这是**转述**，与亲身体验分开标记。
- “还有多久能送到？”：可能只是咨询，除非有明确不满，不应判作投诉。
- “更新以后更流畅了，但我怀念旧入口”：记录正面性能评价与负面/建议性导航反馈。
- 多语言反馈：保留原始语言，可加中文概括，避免因翻译丢失否定、模糊程度和语气。
- 反馈包含不实推测、攻击性语言时：保留与问题有关的可验证事实，避免将攻击性判断转写成客观事实。

## 6. 编码一致性自检

- 同义主题命名是否统一？多主题是否被遗漏？
- 分类是否能由原话解释？是否过度推测动机？
- 对含糊评价是否使用“无法判断”或适度置信度？
- 如果用户指定分类体系，是否优先遵守并注明不适用/新增类别？
