# 用户、人群与场景价值分析

## 1. 分析目标

不要为了营销而先虚构用户画像。先从用户提供的证据识别任务、需求和场景，再判断哪些人群可能更重视相关价值。

## 2. 可用信息来源

优先使用：
- 用户访谈、问卷、客服记录、评论和评价；
- 销售/售前记录、退货原因、常见异议；
- 产品使用数据及明确的指标口径；
- 用户提供的目标市场、行业、岗位和业务背景；
- 产品本身的使用条件与适用范围。

外部公开信息仅在任务需要且具备检索能力时补充，并注明来源、日期和样本局限。

## 3. 场景拆解框架

对每个潜在人群/场景记录：

| 项目 | 说明 |
|---|---|
| 用户/角色 | 谁在使用、购买、决策或影响选择 |
| 触发情境 | 什么情况下开始寻找解决方案 |
| 当前任务 | 用户想完成什么 |
| 当前做法 | 现有工具、人工流程或替代方案 |
| 障碍/痛点 | 当前方式的困难，必须有依据或标记为假设 |
| 选择标准 | 用户可能关注的成本、质量、体验、风险等 |
| 产品匹配点 | 产品哪项已知特点可能有帮助 |
| 顾虑与限制 | 价格、学习成本、兼容性、信任、风险等 |
| 证据状态 | 访谈/数据/反馈/资料陈述/推断/待验证 |

## 4. 人群表达差异

同一产品可能对不同角色有不同价值：
- 实际使用者关心任务完成、操作体验和学习成本；
- 购买者关心价格、回报、风险和替代方案；
- 管理者关心流程、协作、可控性和整体成本；
- 技术决策者关心兼容、部署、安全、维护和集成。

这些只是分析视角，不代表每个产品都必须套用所有角色。应根据实际产品和证据选择。

## 5. 需求证据与假设

必须区分：
- **直接证据：** 用户明确表达的需求或反馈；
- **行为证据：** 有口径的数据、使用行为或购买行为；
- **间接线索：** 销售异议、客服问题、搜索词等；
- **分析假设：** 从产品特点或行业常识推导出的潜在需求。

不得将单条评论写成“用户普遍认为”，不得将样本频次写成总体比例，除非样本设计和统计口径支持。

## 6. 交付建议

输出“人群 × 场景 × 价值”矩阵，避免只给宽泛画像。每个场景应有：
- 人群/角色；
- 具体任务；
- 需求或障碍；
- 对应产品事实；
- 可表达的价值；
- 证据状态；
- 适用限制。
