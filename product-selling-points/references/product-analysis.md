# 产品事实提取与价值链分析

## 1. 产品事实底稿

建议按以下维度提取，不要求每个产品都具备全部字段：

| 维度 | 应提取内容 | 注意事项 |
|---|---|---|
| 身份信息 | 名称、类别、型号、版本、地区、套餐 | 避免混淆不同版本 |
| 功能/服务 | 功能、服务项目、交付内容、使用方式 | 区分已上线与规划中 |
| 规格参数 | 尺寸、材质、容量、性能、兼容性等 | 保留单位和测试条件 |
| 使用条件 | 设备、网络、环境、权限、前置条件 | 不遗漏依赖条件 |
| 体验信息 | 操作流程、界面、服务流程、售后 | 区分设计描述与实测结果 |
| 商业信息 | 价格、套餐、订阅、保修、退换政策 | 记录时间和适用范围 |
| 证据材料 | 官方文档、测试报告、用户反馈、认证 | 标记来源和可信程度 |

## 2. 事实状态

使用以下状态，避免将不同确定性混为一谈：

- **已确认：** 可由明确、适当的证据直接支持。
- **资料声称：** 出现在用户材料、宣传页或供应商描述中，尚未独立验证。
- **推断：** 根据已知产品事实合理推导的潜在价值。
- **待验证：** 需要测试、调研、数据或补充材料。
- **未知/冲突：** 没有足够信息或来源彼此矛盾。

“官方宣传资料”可以支持“官方资料称其具备某功能”，但不一定足以支持性能效果或优于竞品等结论。

## 3. 价值链

对每个候选卖点尽量建立：

| 层级 | 关键问题 | 示例（仅说明推导方式） |
|---|---|---|
| 产品事实 | 产品实际具备什么？ | 支持预约启动 |
| 功能作用 | 功能让用户可以做什么？ | 提前设置启动时间 |
| 用户任务 | 用户想完成什么？ | 按固定时间准备饮品 |
| 潜在收益 | 可能改善什么？ | 减少早晨的手动操作 |
| 场景 | 什么时候有价值？ | 有固定晨间作息时 |
| 证据 | 如何确认？ | 说明书、实际测试、用户反馈 |

不得跨越证据直接推导量化收益。例如，支持自动化不等于一定节省 30 分钟；支持 AI 不等于准确率领先。

## 4. 区分卖点类型

- **功能卖点：** 产品能做什么。
- **性能卖点：** 速度、精度、容量、稳定性等可验证指标。
- **体验卖点：** 操作、设计、流程、服务体验。
- **成本/效率卖点：** 价格、时间、资源或流程成本；需要计算口径和证据。
- **场景卖点：** 在具体情境下的适用价值。
- **服务保障卖点：** 售后、交付、支持、培训等。
- **情感/身份价值：** 使用带来的审美、表达或身份体验；应避免擅自推断用户心理。
- **生态/兼容卖点：** 与工具、系统、渠道或服务的连接能力；明确支持范围。

## 5. 不要把以下内容自动当成卖点

- 仅仅是行业常见配置；
- 无法说明用户收益的技术名词；
- 没有测试口径的“更快、更准、更安全”；
- 没有证据的“行业第一、领先、唯一”；
- 产品路线图或未上线功能；
- 单个用户反馈代表的普遍结论；
- 与目标受众无关的参数堆砌。

## 6. 结果建议

每个重要卖点至少回答：
1. 卖点是什么？
2. 对谁有价值？
3. 在什么场景下有价值？
4. 有什么证据？
5. 有什么条件或限制？
6. 为什么优先于其他卖点？
