# 测试用例质量审核标准

## 1. 单条用例质量

每条用例检查：

### 明确性
- 测试目标单一且明确；
- 测试对象和模块清楚；
- 前置条件完整；
- 输入数据具体；
- 执行步骤可复现；
- 预期结果可观察；
- 验收标准可判定。

### 可执行性
- 不依赖未说明的账号、权限、文件或环境；
- 步骤没有“适当操作”“正常填写”等模糊描述；
- 测试数据有足够细节；
- 依赖条件不可用时标记 Blocked/待确认。

### 可验证性
- 有明确断言；
- 能区分 Pass/Fail；
- 对非确定性输出有 rubric；
- 对外部副作用有状态或日志证据。

### 独立性
- 尽可能避免多个无关目标混在一条用例；
- 用例之间的依赖要显式说明；
- 可重复执行或说明执行后的清理方式。

## 2. 用例集质量

- 需求/功能点是否有对应测试；
- 核心主流程是否覆盖；
- 是否覆盖适用的异常、边界、反向场景；
- 角色、状态、参数组合是否合理；
- 是否存在重复或近似重复用例；
- 是否覆盖历史缺陷；
- 是否包含高风险路径；
- 是否有不适用维度及理由；
- 用例数量是否符合用户要求。

## 3. 重复检测

若两条用例的测试目标、触发条件、关键输入类别和预期行为实质相同，仅改写措辞或替换实体名称，应视为重复。

若输入不同导致业务分支、状态、权限或风险发生变化，则可作为独立用例。

## 4. 常见不合格写法及修正

不合格：“检查登录是否正常。”
修正：“使用已注册且状态正常的账号提交正确密码；预期登录成功，跳转到首页，登录态建立，刷新后仍保持登录（若产品要求持久会话）。”

不合格：“输入错误数据，系统提示错误。”
修正：“将手机号字段输入 9 位数字并提交；预期阻止提交，提示手机号格式不正确，且不创建用户记录。”

不合格：“测试 AI 回答质量。”
修正：“提供包含两个互相冲突约束的请求；检查 Agent 是否识别冲突、主动澄清或明确说明取舍，不得静默忽略其中一项。”

## 5. 覆盖率口径

可计算：
- 需求覆盖率 = 已关联至少一条用例的需求数 / 纳入范围的需求总数；
- 功能点覆盖率 = 已覆盖功能点数 / 纳入范围的功能点总数；
- 风险覆盖率 = 已有测试验证的风险项数 / 纳入范围的风险项总数。

必须先定义分母和范围。不得以“用例条数/功能数”计算覆盖率。若需求清单不完整，应标记为估算或不可计算。

## 6. 审核结论
- 可执行：关键字段齐全，能直接执行；
- 需完善：存在可修正的步骤、数据或验收标准问题；
- 不可执行：关键前置条件或预期规则缺失；
- 重复：与其他用例实质重复；
- 待确认：依赖未明确的业务规则或环境信息。
