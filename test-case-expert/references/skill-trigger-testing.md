# Skill 触发专项测试

## 目标
验证 Skill 在应该触发的请求中能被正确发现和调用，在不应该触发的请求中不会无故介入，并能与相似 Skill 区分。

## 测试集结构

### A. 正向触发
1. 直接使用 Skill description 中的核心任务表达。
2. 使用常见同义词。
3. 使用自然语言描述，不出现 Skill 名称。
4. 使用行业术语或用户常用口语。
5. 使用具体任务场景，而不是功能名称。

### B. 负向触发
1. 只讨论相关概念，不要求执行。
2. 请求与 Skill 相邻但超出职责。
3. 请求明显属于其他 Skill。
4. 仅在背景中提及关键词。
5. 用户明确表示只想了解知识，不需要执行。

### C. 模糊与边界触发
1. 信息不足但目标可能匹配。
2. 多个任务混合。
3. 用户表达不完整或存在错别字。
4. 目标对象不明确。
5. 用户在对话中途改变任务。

### D. 多 Skill 冲突
1. 两个 Skill 功能高度相似。
2. 一个请求包含多个 Skill 的职责。
3. 一个 Skill 是主任务，另一个只是辅助能力。
4. 多 Skill 都可匹配时，检查平台是否按描述和优先级选择合理。

## 用例必须包含
- 用户完整输入；
- 预期触发：Yes / No / Clarify / Multi-skill；
- 预期 Skill；
- 触发理由；
- 实际加载/调用证据；
- 失败分类。

## 判定注意事项
- “出现关键词”不等于应该触发。
- 正向触发要以任务意图为依据。
- 负向触发必须选择语义相近但职责不同的请求，不能只用完全无关的话题凑数。
- 平台未加载 Skill：记为触发/平台集成问题。
- Skill 已加载但执行偏离：记为指令/流程执行问题。
- 无法观察加载状态：标记 Inconclusive，不得猜测。

## 常见语境与路由边界

触发识别按“用户主要想完成什么”判断，不要求出现“测试用例”四字，也不能只靠关键词匹配。

| 请求语境 | 典型表达 | 预期工作模式 |
|---|---|---|
| 显式测试 | “测试一下这个功能/脚本/应用”“帮我做接口测试” | 测试设计/用例生成；若明确要求真实执行，再核对环境、权限和副作用 |
| 用例工作 | “写测试用例”“这些用例缺什么”“帮我优化用例” | 新建、补充或审核用例 |
| 质量验证 | “这个流程能跑通吗”“是否满足需求”“还有没有遗漏” | 按对象设计验证场景，缺少运行环境时明确给设计而不假称执行 |
| 故障排查 | “偶尔失败”“怎么稳定复现”“修复后要回归什么” | 缺陷复现/回归场景；根因未知时标假设 |
| 上线验收 | “上线前检查什么”“帮我验收功能” | 验收范围、标准和风险优先的用例 |
| 纯知识 | “什么是边界值分析”“解释软件测试流程” | 解释概念，不自动生成针对某对象的用例 |
| 开发/修复 | “直接实现这个功能”“帮我改代码修 Bug” | 以开发/修复为主；除非用户还要验证，否则不把用例设计当成唯一任务 |
| 普通代码审查 | “审查代码结构/风格”且不涉及行为验证意图 | 不冒充完整代码审查；如用户关注正确性/异常/风险，可明确以测试视角补充 |

若一句话包含开发与测试两项任务，按用户实际请求都处理；不能因触发 Skill 而丢弃主要开发任务。请求只说“检查一下”且对象/目标都不清时，优先基于现有上下文做最小可用判断，只有关键缺口影响结论才澄清。

- `intent_matched`
- `negative_trigger_rejected`
- `ambiguity_handled`
