# AI Agent 与 Skill 专项测试

## 1. 测试目标

AI Agent/Skill 由自然语言指令、模型行为、上下文、工具、文件和平台运行机制共同构成。测试必须同时关注：
- Skill 是否被正确发现、加载和触发；
- 是否理解用户真实意图；
- 是否遵守 Skill 的指令和流程；
- 是否正确使用参考文件、脚本和工具；
- 是否完成任务并交付可信结果；
- 是否在边界、异常和对抗输入下保持安全；
- 是否在重复调用和不同平台下保持合理稳定。

**不要把“回答看起来不错”当成 Skill 测试通过。** 需要检查行为、过程、产物和结果证据。

## 2. 测试前的静态解析

收到 Skill 包、目录或 `SKILL.md` 后，先检查：

### 元数据
- name、description 是否存在且清晰；
- 名称、描述是否与实际能力一致；
- 触发描述是否覆盖主要意图；
- 是否过度宽泛导致误触发；
- 是否存在不合理的触发限制。

### 指令
- 角色、目标、输入要求是否明确；
- 工作流是否有可执行步骤；
- 条件分支和完成条件是否明确；
- 是否存在互相冲突或重复规则；
- 是否定义异常、拒绝和降级行为；
- 是否规定输出结构和质量标准。

### 文件结构
- references、templates、scripts 等路径是否存在；
- 文件引用是否正确；
- 是否存在失效路径、遗漏文件或重复资料；
- 文件内容是否与 SKILL.md 一致；
- 是否把必要指令错误地放在未被加载的文件中。

### 脚本与工具
- 脚本语言、入口、参数、依赖和权限；
- 是否存在危险命令、硬编码密钥或不必要网络访问；
- 工具名称、参数 Schema、调用条件；
- 工具失败时是否有处理逻辑。

静态检查只能说明文件结构和指令设计情况，不能代替实际调用测试。

## 3. 十三类专项测试维度

### 3.1 触发准确性
- 正常触发：直接提出 Skill 核心任务。
- 语义触发：不同措辞表达相同目标。
- 自然表达触发：不出现 Skill 名称或关键词。
- 模糊触发：信息不完整但可能属于目标场景。
- 负向触发：相似话题但不属于 Skill 职责。
- 过度触发：只是讨论概念，不要求执行。
- 多 Skill 冲突：多个 Skill 职责相似时能否正确区分。
- 复合请求：一句话包含多个任务时是否正确判断。
平台未加载 Skill 与 Skill 加载后执行失败必须分开记录。

### 3.2 功能完整性
把 description 和正文中声明的能力逐项拆成可测试功能点。每项至少有一个验证场景；核心能力应覆盖正常、复杂或异常条件。不得只用一个宽泛问题代表全部功能。

### 3.3 指令遵循
- 是否遵守角色、语气、规则和限制；
- 是否执行必需步骤；
- 是否使用指定结构；
- 是否遵守输出长度、语言、格式；
- 用户要求偏离规则时是否按优先级处理；
- 是否遗漏禁止事项或完成条件。

### 3.4 工作流执行
- 步骤顺序是否正确；
- 必要阶段是否被跳过；
- 前置条件未满足时是否继续；
- 分支选择是否正确；
- 是否过早给结论；
- 是否陷入重复、循环或无效追问；
- 达到完成条件后是否正确收尾。

### 3.5 多轮交互与上下文
- 是否记住前轮关键事实；
- 是否正确处理用户补充和纠正；
- 用户修改条件后是否更新后续结果；
- 是否区分新旧信息及冲突信息；
- 用户中途改变目标时是否重新规划；
- 是否在会话切换或长上下文下出现信息串扰；
- 是否重复询问已经回答的问题。

多轮用例必须提供完整的轮次序列，并逐轮定义预期行为，不能只给第一句。

### 3.6 输入处理
- 缺少必要信息；
- 多余信息、无关信息；
- 相互矛盾的信息；
- 超长文本、特殊字符、多语言；
- 上传文件缺失、格式错误或内容不完整；
- 用户拒绝提供信息；
- 用户提供错误或误导性前提。

### 3.7 输出质量
检查准确性、完整性、相关性、逻辑性、专业性、可执行性、一致性和事实依据。根据 Skill 领域选择指标，不要求所有 Skill 使用同一评分维度。

### 3.8 输出规范
- 标题、章节、表格、字段是否完整；
- JSON/YAML/CSV 等是否可解析；
- 是否满足字数、语言和格式要求；
- 文件是否实际生成；
- 文件路径、链接、名称和内容是否正确；
- 是否出现多余内容或漏交付。

### 3.9 工具调用
- 是否选择正确工具；
- 参数、字段、类型和必填项是否正确；
- 调用顺序和调用次数是否合理；
- 是否误调用、漏调用或重复调用；
- 工具失败时是否解释、重试或降级；
- 是否验证工具结果而非臆造成功。

### 3.10 文件与参考资源
- references 是否被实际使用；
- 是否引用正确文件和版本；
- 文件解析是否完整；
- 是否把 README 图片、示例或元数据误当成用户输入；
- 是否正确处理空文件、损坏文件和不支持格式；
- 输出文件是否存在、可打开且内容完整。

### 3.11 异常与边界
- 任务范围外请求；
- 输入缺失、冲突或不合法；
- 外部工具不可用；
- 文件读取失败；
- 运行超时、用户中断；
- 多个要求冲突；
- 依赖资源失效；
- 失败后能否安全恢复。

### 3.12 安全性
- 提示词注入和指令覆盖；
- 恶意参考文件或工具输出；
- 越权读取、写入、删除或外发；
- 系统提示词、密钥和隐私泄露；
- 不安全代码执行；
- 未经授权的外部副作用；
- 对危险或超范围请求的安全处理。

### 3.13 稳定性与兼容性
- 相同输入多次运行；
- 同义表达和输入顺序变化；
- 长上下文和多轮任务；
- 模型版本变化；
- 不同 Agent 平台；
- 工具可用性变化；
- 网络和文件环境变化。

## 4. Skill 测试用例设计流程

1. 从 Skill 声明中提取能力清单。
2. 将每项能力映射到 13 个维度中的适用项。
3. 区分平台触发、Skill 逻辑、工具依赖和模型输出问题。
4. 为每个核心能力设计至少一个可验证场景。
5. 对多轮流程设计完整轮次。
6. 对工具/脚本设计参数、失败和恢复用例。
7. 对输出设计规则断言和语义评价标准。
8. 对安全和副作用设计安全、授权的测试场景。
9. 首次默认输出 10 条，按风险动态分配。
10. 进行覆盖、重复和可执行性审核。

## 5. Skill 测试结果分类

每条测试记录应区分：
- **Pass**：有证据表明达到验收标准。
- **Fail**：有证据表明未达到验收标准。
- **Blocked**：环境、权限、依赖或前置条件阻止执行。
- **Inconclusive**：证据不足，无法判断。
- **Not Run**：尚未执行。

进一步定位问题归属：
- 平台发现/加载/触发；
- Skill 指令或流程设计；
- 参考文件或资源；
- 脚本/工具/MCP/API；
- 模型输出质量；
- 测试环境或测试数据；
- 证据不足，待排查。

不要仅凭输出不理想就断言是模型问题，也不要在 Skill 未加载时将其记为 Skill 功能失败。

## 5. 从 Skill 包声明建立可验证清单

收到 `SKILL.md` 或完整 Skill 包时，先把要验证的声明转成“声明—行为—证据”清单，再选用例；不要求每个 Skill 都具备脚本或工具。

| 对象部分 | 静态检查能说明什么 | 需要运行证据的行为 |
|---|---|---|
| 基础信息与触发描述 | 名称、描述、功能范围、正反触发示例是否一致 | 平台是否发现/加载；自然表达是否触发或拒绝 |
| 指令与流程 | 角色、前置条件、分支、完成条件、限制是否明确一致 | 模型是否遵循顺序、补问关键缺口、正确结束 |
| 输入与输出 | 声明的输入、文件类型、字段、格式、交付物 | 实际解析能力、完整性、文件是否可用、格式是否合格 |
| references/templates | 路径存在、主文引用正确、内容相关且无矛盾 | 运行中是否按需读取并采用正确规则 |
| 脚本/工具/接口 | 入口、参数、依赖、权限和副作用设计 | 真实环境的调用参数、结果、错误处理和副作用 |
| 安全约束 | 文本是否声明权限边界、拒绝和数据保护要求 | 对抗输入下是否守边界；不能以静态措辞推断有效 |

不要把“写了支持”当成该能力已接通。若 Skill 宣称生成报告、读取资料、调用工具或生成文件，应各自定义可观察产物/调用证据和失败条件。

## 6. 专项用例设计的最低覆盖

按 Skill 的真实功能、风险和用户目标筛选，不要求每个用例集覆盖所有维度；对声明为核心的每项能力至少映射一条用例。对于通用 Skill，通常考虑以下维度：

1. **触发准确性：** 显式调用、同义改写、自然表达、负向相邻请求、知识讨论、模糊请求及多 Skill 冲突。
2. **功能完整性：** 逐项验证描述和正文声明的主要能力，而非用一个宽泛提示代替。
3. **指令遵循：** 用户要求与 Skill 约束冲突、格式要求、限制、拒绝及结束条件。
4. **工作流执行：** 顺序、分支、前提、必要阶段、重复追问、过早结论和完成状态。
5. **多轮与上下文：** 信息补充/纠正、目标改变、信息冲突、会话延续及适用的跨会话隔离。
6. **输入处理：** 缺失、无关、矛盾、错误、超长、多语言和文件内容不完整。
7. **输出质量：** 任务完成、准确、完整、相关、有依据、可执行且符合领域要求。
8. **输出规范：** 必需章节/字段、结构可解析、文件真实存在且内容完整。
9. **工具调用：** 工具选择、参数、顺序、次数、权限和失败/重试/降级。
10. **文件与资源：** 引用路径、资料读取、格式限制、损坏/空文件及产物核验。
11. **异常与边界：** 工具不可用、超时、中断、用户取消、超范围请求和恢复。
12. **安全性：** 提示注入、越权读取/写入、隐私暴露、危险命令和未授权副作用。
13. **稳定性与兼容性：** 核心输入的合理语义变体、上下文长度、重复运行及声明的宿主/模型差异。

### 6.1 专项测试组合建议

一组精简的首次用例可从以下方向组合，再按风险和需求调整：核心能力、正向触发、自然表达、相邻负向请求、多轮流程、输入缺失/纠正、输出/结构、工具/文件或高风险路径。十条默认量不是维度配额；若某项能力不适用，写明理由并将名额转给核心风险。

多轮场景应写全每一轮用户输入及逐轮预期行为。若例子使用“人生选择”“下单”等领域任务，预期必须以被测 Skill 的实际规则为依据，不可将例子升格成普适流程。

### 6.2 变体与可比性

当核心任务依赖自然语言或模型判断时，围绕同一目标生成有限且有目的的变体，例如同义表达、上下文长短、信息完整/缺失、语言、角色、工具可用状态。说明每个变体改变了哪个条件，避免只有措辞变化却被计作独立功能覆盖。

对比运行前固定 Skill 文件版本、宿主/客户端、模型、工具和权限。模型或环境变化时单列结果，不混为一次通过；相同输入的重复次数按风险决定并记录，不凭少量成功样本声称稳定率。

## 7. 结果与问题归属的记录

建议每条用例记录：

- Skill ID/版本、宿主/客户端、模型、日期和工具权限（已知部分）；
- 请求方式（显式/自然语言/自动入口）、预期触发状态（触发/不触发/澄清/多 Skill）；
- 平台发现/加载证据（如平台可观察）、完整输入/多轮序列、预期行为；
- 实际输出、调用轨迹、产物或脱敏日志；
- Pass/Fail/Blocked/Inconclusive/Not Run 及失败归属。

若平台不提供加载状态，保留“无法观察/无法判定”，不以回答风格推断已加载。若加载了错误版本，先记录版本/装载问题，再判定当前执行是否能支持对候选内容的结论。
